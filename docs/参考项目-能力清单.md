## 二、按需求逐项对照

### 1. 视频采集 —— 有两条路

**路线 A：AVScreenCapture Surface 零拷贝**（ohscrcpy `capture.cpp`）
- `StartScreenCaptureWithSurface(encoderSurface)` 把采集结果直接写进编码器输入 Surface，全程不走回调
- 约 30fps，实测解码滞后 45ms，端到端约 100ms
- 普通 App 权限下需要走系统录屏授权

**路线 B：虚拟屏（无头采集）**（ohscrcpy `virtual_display.cpp`）
- 自建名为 DevEcoViewer 的虚拟屏（靠 WMS 白名单），编码器 Surface 作为该屏渲染目标，`SetVirtualScreenAsDefault()`
- **这是唯一有希望"熄屏也出画面"的路径**，但需系统级权限 + 整机编译
- 致命短板：虚拟屏一旦设为默认屏就无法销毁，只能重启设备

**路线 C：华为 hosScrcpy 中间件**（HOScrcpy / hnscrcpy 都在用）
- 设备端推 `libscreen_casting.z.so`，起 uitest 扩展守护进程，`hdc fport` 转发，gRPC 收 H.264
- 约 20fps（HOScrcpy）到 50-57fps（hnscrcpy 直解优化后）
- **风险**：闭源 jar 禁商用；固件启用 XPM 签名管控后该变体失效
- ~~**更关键**：走 hdc，本质是 USB/调试通道，与"Wi-Fi 为主"的诉求冲突~~ ← **此条 2026-11-09 判定为错误，已撤销**。hdc 完全可以走无线（本项目的注入通道就是无线 hdc `192.168.1.100:38803`），因此「与 Wi-Fi 冲突」不成立。路线 C 的真实门槛只剩两条：**闭源 jar 禁商用** + **XPM 签名管控风险**。

> **2026-11-09 重大补充（务必先读）**：读完 `HOScrcpy-python-main` 源码并真机实测，确认**路线 C 是可行的、且全程不弹录屏授权框**。
>
> 关键机制：采集 so（`libscrcpy_server*.z.so` → 推到设备固定名 `libscreen_casting.z.so`）由 **uitest 扩展守护进程**加载，内部走 `NativeStartScreenCopy`（系统内部能力，非公开 SDK 的 `AVScreenCapture`），再经 `hdc fport` → `localabstract:scrcpy_grpc_socket` → gRPC `ScrcpyService/onStart` 服务端流取裸 H.264。
>
> **为什么它不用授权**：整个参考项目源码里**搜不到 `AVScreenCapture`，也搜不到「授权/弹窗」任何字样** —— 它根本不走需要用户授权的公开接口。
>
> **本项目真机实测（平板 MLR-AL00，03:16~03:23）**：设备上早已有 `libscreen_casting.z.so`（6.9 版，247989B）；起守护进程后 `@scrcpy_grpc_socket` 出现；gRPC 收流正常（首块 31B / 307ms，头部 `0000000167640034` = 标准 H.264 SPS+PPS；8 秒 38 块 / 160795B）；**截图确认全程无授权弹窗**。
>
> **对我们的意义**：当前 `AVScreenCapture` 路径每次冷启动要用户点一次授权框；这条路能彻底免掉。代价是重新引入「华为闭源 so + 依赖 hdc + 许可不确定性」。**技术可行，但切换与否需用户决策。**
> 未验证项：帧率/画质上限（参考项目默认 20fps/2Mbps，远低于我们 60fps/16Mbps 目标）、so 与 API 26 的兼容性、长时间稳定性。

### 2. 输入注入 —— 三档，按延迟与权限取舍

| 手段 | 延迟 | 依赖 | 谁在用 |
|---|---|---|---|
| MMI `SimulateInputEvent` + PointerEvent/KeyEvent | 系统级最优 | 系统权限/整机 | ohscrcpy |
| uitest 持久 socket 直发 Gestures JSON | <1ms（move 限流 20Hz） | 调试授权 | HOScrcpy `fast_touch.py`、hnscrcpy |
| `uinput -M` / `uinput -K` 子进程 | ~100ms（逐键快通道可到 130ms 整批） | 调试授权 | HOScrcpy、hnscrcpy |
| 辅助功能 / VirtualHid / ShellAgent | 中 | 辅助授权或 ADB/Root | lanlink |

**本项目实测（2026-11-08，平板 MLR-AL00）**：第 2 档已打通并定档为产品路径 ——
`uitest start-daemon singleness &`（加载 `/data/local/tmp/agent.so`，取自 DevEco 自带 `hosScrcpy-1.0.20-beta.jar` 的 `uitest_agent_1.2.3.so`）→ `hdc fport tcp:<local> localabstract:uitest_socket`（**抽象 unix socket，不是网上传的 tcp:8012**）→ 报文 `_uitestkit_rpc_message_head_` + u32 sid(大端) + u32 len(大端) + JSON + `_uitestkit_rpc_message_tail_`，JSON 的 module 固定 `com.ohos.devicetest.hypiumApiHelper`、method 为 `Gestures`。
实测：touchDown 单程 p50 12.94ms、touchUp 9.13ms；C# 端到端单点 p50 74.97ms / p95 90.42ms（20 次 0 失败）；`pressBack` p50 149.86ms、`pressHome` p50 304ms（hypium 语义化 API，内部等 UI 稳定，不是通道慢）。
第 1 档需系统签名、第 3 档受 hdc 进程模型限制（冷态 2s）、第 4 档本机 ROM 无「扩展服务」入口 —— 三条均排除。

**第 4 档已于 2026-11-09 升级为系统级取证（结论不变，证据更硬）**：本机设置菜单实际名为「关怀和无障碍」，搜「无障碍」只返回「无障碍快捷键」，**没有「扩展服务 / 已安装的服务」列表**；`hidumper -s AccessibilityManagerService -a '-c'` 返回 **`client num: 0`**（零客户端注册），`-u` 显示 `accessible:0 / gesture:0`。对照应用侧 `bm dump` 登记**完全正常**（LowFreqAccessibility `type:4` / `visible:true`）—— 即**问题在平台不提供挂载入口，不在应用声明**。再叠加 API 层：整套 `AccessibilityExtensionContext` 自 API 12 起全方法 deprecated 且无 `useinstead`。**双重死路，不要再找那个菜单，也不要再试应用内直连。**（参考项目里走这条路的是 lanlink，它依赖的是有辅助授权入口的环境。）

**「设备内直连」这条路走不通（2026-11-08 实测判死）**：曾设想让平板应用进程自己连 `@uitest_socket`，PC 只发 HWP UDP，从而彻底摆脱 hdc / 无线调试。真机验证结果：应用进程内 `connect()` 直接返回 `errno=13 (EACCES)`、`peerUid=-1`、零字节回包。原因是 SELinux 跨域 —— 应用进程域 `o:r:debug_hap:s0:...`（正式包 `normal_hap`），agent 进程域 `u:r:uitest:s0`，`debug_hap → uitest` 的 `unix_stream_socket connectto` 未放行。**不是 agent 做了 UID 白名单**：`agent.so` 里与 Peer UID 相关的只有一行日志格式串 `Got connection from domain socket, Peer PID: %d, Peer UID: %d, Peer GID: %d`，没有任何 reject 分支。也不能靠 `dlopen` 把 agent.so 拉进应用进程自起 RPC（虽然它导出了 `OHOS::uitest::RpcServer::StartService` 等 548 个符号）—— 注入最终落到 MMI，仍要 uitest 域身份。**结论：第 2 档必须由 PC 侧经 hdc fport 接入；同域内直连、应用连本地 hdcd 8710 都不必再试。**

要点：键盘中文必须走 `uitest uiInput inputText`（uinput 只能发键值）；文本注入要**攒批 + 锚点坐标**（hnscrcpy `TextInjector.java`）；触摸事件必须**串行化并节流**，否则乱序。

### 3. 剪贴板 —— 只有 oink 做全了

- HOScrcpy：单向文本（PC→设备），无图片
- hnscrcpy：单向文本，靠工具条按钮注入最后点击的输入框
- ohscrcpy：无
- lanlink：文本 + 文件清单，无位图；SHA-256 指纹防回环；10 分钟 30 条历史
- **oink**：Text / HTML / RTF / **PNG 位图** / 文件 / Custom / Native 全格式；**按需拉取 + 内容 promise**（避免大图阻塞主链路）+ 隐私标记透传 + 防回环

要双向且支持图片，直接抄 oink 的 `crates/oink-clipboard/src/{sync,formats,content/promise}.rs` 模型，别从 HOScrcpy 的单向文本往上加。

### 4. 多设备（≤3 台）—— 有三套现成范式

- **单编码器多观看者租约**：lanlink `SharedVideoSource.java`，一台目标同时只允许一个输入源
- **serial → 窗口映射**：hnscrcpy `App.java`，多窗口并发
- **一机一进程 + 端口槽位**：ohscrcpy `-t` 参数

3 台的量级，租约模型（谁在控制谁）比并发更关键——否则三台设备抢焦点会乱。

### 5. 息屏 / 锁屏不中断 —— ⚠️ 五个项目都没解决

- hnscrcpy README 明确写：**锁屏不支持**，系统安全窗口不提供像素，注入也被拦截，黑屏需手动解锁
- oink `input/src/display_power.rs`：显示器休眠时**主动把指针交回源端**，不强行保活
- lanlink：锁屏/UAC 时停注入停采集
- HOScrcpy：只在采集前用电源键唤醒屏幕，无保活
- ohscrcpy 虚拟屏：理论上不接物理显示器也能采集，但需系统权限，且默认屏不可撤销

**结论：这是本项目唯一的真·未知项，必须先做技术验证再谈架构。**

### 6. 传输与组网

- lanlink 的"先认证 TCP、再升级 QUIC"渐进通道设计（`src/quic.js` + `native/quic/src/lib.rs`）：握手稳、传输快，值得抄
- oink 的 `crates/oink-network/src/link/`：连接池 + 路径迁移 + 心跳 + 双拨择优 + 中继切换
- 发现层：mDNS + 自研 UDP beacon，**发现结果视为不可信线索**（oink 这条安全约定很实在）
- 配对：lanlink SRP-6a 8 位码；oink SPAKE2 + ed25519 + 自签 TLS
- 码率：lanlink `src/adaptive-video.js` 自适应 0.5–8Mbps

## 五、三条硬结论

1. **采集方式决定项目天花板**。走 hdc + 华为 jar 能快速出活，但绑死调试通道、受 XPM 管控、禁商用；走 AVScreenCapture 自主可控但要处理授权与虚拟屏。这个选择要在写第一行代码前定。
2. **锁屏/息屏保活没有现成答案**。必须先写验证 Demo 证明可行，否则需求 8 无法承诺。
3. **剪贴板直接照 oink 的格式模型设计**，一次性把图片和富文本做进去，别留后补。

## 六、hnscrcpy 代码级复核（2026-11-11）

> 触发：用户问「参考 hnscrcpy 是不是可行」。本节不再是读 README 归纳，而是**逐文件读源码**的结论。
> 复核范围：`TextInjector.java`、`DeviceShell.java`、`MirrorSession.java`、`MirrorWindow.java` + 完整文件树
> （仓库 `taxiao213/hnscrcpy`，MIT 之外自有代码 Apache-2.0，**内置华为 jar/hdc 禁商用**）。
> **本节结论已足够，项目完成后不必再回读该仓库。**

### 6.1 定位与栈

Java 17 + JavaFX 21 + JavaCPP(FFmpeg 7.1) + 内置四平台 hdc 二进制。视频源 = 华为 hosScrcpy jar
（`hosScrcpy-1.0.20-beta.jar`，运行期反射定位，不参与编译依赖）→ gRPC over `hdc fport` 收裸 H.264
→ avcodec 直解 → `PixelBuffer` 零拷贝上屏。**整条链路绑死 hdc 会话**，与本项目「无线 hdc 会互踢、投屏走 UDP」
的硬规则冲突，故这一层不可照搬。

### 6.2 剪贴板：只有单向，反向零实现（关键结论）

`MirrorWindow.onPaste()` 全部逻辑：

```java
var cb = Clipboard.getSystemClipboard();          // 只读 PC 剪贴板
String text = cb == null ? null : cb.getString(); // 只要纯文本
session.textInjector().injectNow(text);           // 只往设备写
```

- **方向唯一**：PC → 设备。
- **全仓无任何读取设备剪贴板的代码**（无 `getPasteData`、无 pasteboard 调用）。
- PRD §3.3 把「剪贴板同步」明确列入 **暂不做（YAGNI）**。
- 另有「输入文本…」对话框（`onTextInput`），本质是同一个 `injectNow`，只是绕过系统剪贴板。
- 结论：**它没有解决「平板复制 → 电脑粘贴」，与我们的实测结论一致，不要再指望这条路。**

### 6.3 文本注入的真实实现（有硬限制）

```java
"uitest uiInput inputText " + x + " " + y + " '" + escaped + "'"
```

| 项 | 实现细节 |
|---|---|
| 通道 | 设备自带 `uitest uiInput inputText`，走设备 IME，**天然支持中文** |
| 坐标 | **必须是「最后一次触摸」的设备坐标**；没点过输入框就 `text dropped (no anchor)` 直接丢弃 |
| 攒批 | 打字字符进 `StringBuilder`，静默 `IDLE_FLUSH_MS=80ms` 后整批注入（一次 shell RPC 比逐字符快一个数量级） |
| 分片 | 单次注入 `MAX_SLICE=2000` 字符，防命令行参数溢出 |
| 换行 | 按 `\n` 拆段，段间注入 `uinput -K -d 2054 -u 2054`（KEY_ENTER） |
| 转义 | 文本包单引号，内部 `'` 转成 `'\''`；`\r\n`→`\n`；`<0x20` 控制字符剔除 |
| 串行 | 单线程 `text-inject` 执行器 + `text-flush` 调度器，天然串行 |
| 冲刷 | `flushSync()` 有界等待 2500ms（旧值 5s，体感卡死） |
| 失败 | 输出含 `[Fail]` 记 `TEXT_INJECT_FAILED` 诊断事件 |

`DeviceShell.exec()` 双通道：优先 `bridge.executeShellCommand`（hosScrcpy 常驻连接，免本地进程开销），
抛异常才回退 `hdc.shell` 子进程。

**对本项目的判定**：能力真实可用，但前提是「先点一下输入框」。若要做 PC→平板，我们只能把文本经自己的 UDP
链路发到平板 App，**平板 App 内没有 `uitest` 等价能力**（UiTest 仅测试签名可用，`inputEventClient` 已证死），
所以要落地仍得靠一条低频 hdc shell（无线 hdc 冷态 2~3s 重连）。**不是纯注入就能做**。

### 6.4 静默断流看门狗（本项目最该抄的部分）

`MirrorSession` 常量：

```java
WATCHDOG_INTERVAL_MS  = 10_000;   // tick 周期
STARTUP_GRACE_MS      = 30_000;   // 首帧宽限，期内只催 IDR 不判死
INPUT_ACTIVE_WINDOW_MS= 15_000;   // 输入预言机窗口
PASSIVE_RECONNECT_TICKS = 30;     // 纯静默兜底 ≈ 5 分钟
```

判死纯函数（可单测）：

```java
static boolean shouldReconnectOnSilence(boolean probeAlive, int silentTicks, boolean inputActive) {
    if (inputActive && silentTicks >= 2) return true;  // 有输入却画面不变 → 真死
    if (!probeAlive) return true;                      // 探活失败 → 死
    return silentTicks >= PASSIVE_RECONNECT_TICKS;     // 静默满 30 轮才兜底
}
```

配套机制：

- **有帧就清零**：`decodedCount()` 变化 → `silentTicks=0` 且主动 `requestIDRFrame()` 保活。
- **首帧未到**：未超宽限 → 只催 IDR；超宽限 → 判死重连。
- **探活**：`bridge.executeShellCommand("param get const.product.name", 5)`，5s 超时抛异常即判死。
- **输入预言机**：`noteInputActivity()` 在触摸/键盘/粘贴时打时间戳，15s 内有输入却连续 2 轮无帧 → 判死。
- **重要教训（v1.0.3 修的 bug）**：早先「无帧即重连」**每 ~25s 误杀健康流**。静态画面不推帧是
  hosScrcpy 1.0.20 的正常行为，**不能拿帧间隔当断流依据**。我们的 `_awaitKeyframe` 加超时同理，不能简单超时即重连。
- **重连**：指数退避 `1000 << (attempt-1)` 封顶 10s；耗尽 5 次后转 30s 慢速无限重试（不留僵尸窗口）。
  `reconnectPending` CAS 把并发失败**合并为一次**重连。
- **重连前必 `sleep(RECONNECT_SETTLE_MS=2000)`**，等设备侧旧 scrcpy 进程退出，否则新旧实例互踢。
- **close 幂等**：`state=CLOSED` 早退；`watchdogTask.cancel` + `scheduler.shutdownNow` + `textInjector.close`。

### 6.5 其它可直接复用的工程点

| 坑 | 他们的解法 | 对我们的意义 |
|---|---|---|
| 双击后 10s 黑屏 | **窗口先上屏**（预建 `FrameRenderer`，状态栏显示进度），会话在后台线程构造并 `start()` | 我们已做「首帧催帧 + 启动进度」，方向一致 |
| 窗口逐帧无限放大（每脉冲 +512px） | 钉死 `screenHolder` 的 `min/pref = 0`，切断 ImageView→父级 pref→更多空间的正反馈 | 布局类 bug 的经典防法 |
| 降采样逐帧重建 sws（每次 ~18MB） | `desiredOutputSize()` 量化到 `HINT_QUANTUM=8px` + 迟滞，尺寸真变才重建 | 亚像素抖动必须吸收 |
| 裸 H.264 直播管道 | **不用 `FFmpegFrameGrabber`**：`find_stream_info` 会阻塞到 EOF；改 `avcodec` 直解 | 若我们 PC 端改 FFmpeg 需注意 |
| 解码积压 | `ArrayBlockingQueue(8)` 满则**丢最旧**，只留最新帧槽位，解码不在 UI 线程 | 与我们 D3DImage 策略一致 |
| 关窗留僵尸会话 | `setOnCloseRequest` + `setOnHidden` **双挂**，`closeSession` 幂等；cleaner 用**非守护**线程 | 与我们 InstanceGuard 互补 |
| 只标标题栏 ✕ | `onCloseRequest` 仅拦标题栏 ✕，工具条关闭走 `stage.close()` 不触发 | — |

### 6.7 已知限制（他们自己承认）

- **锁屏黑屏**：锁屏是系统安全窗口，截图/投屏 API 都拿不到像素，须先手动解锁 → **反过来印证我们「视觉息屏」降级是对的**。
- 视频恒为设备原始分辨率（降采样只作用于渲染输出）。
- 无音频通道；不支持模拟器；v1 单会话。

### 6.8 一句话收口

**剪贴板方向它和我们一样是死路（它自己列为 YAGNI，代码里一行反向都没有）；真正值得拿走的是看门狗那套
「输入预言机 + 探活 + 首帧宽限 + 静默不误杀」，正好补我们 `_awaitKeyframe` 无超时导致画面永久定格那个账。**
