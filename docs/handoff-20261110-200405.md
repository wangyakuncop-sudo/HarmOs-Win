### 两个「结论性判断」（避免重复排查）

**① 绿边框根因 = 16px 宏块对齐填充**
- `1600/3=533.x` 非 16 倍数 → 编码器补零到 544×864 → 补零区经 BT.601 limited 解出 **(0,154,0) 纯绿**
- 与截图实测绿线 **(0,152,0)** 吻合；devscale 1/2/4 可被 16 整除故从不出现
- 修法：解码后按内容尺寸裁剪。**⚠️ 关键陷阱**：`Nv12ToBgra` 的 UV 平面偏移是 `stride × bufH`（缓冲高度），**不是** `stride × h`（裁剪高度），用错会让色度整幅错位且不报错

**② 「红字偏粉紫」是 App 自身配色，非管线缺陷（已双证据定论）**

| 来源 | 时间戳红字 | B−G |
|---|---|---|
| 平板原生截图（`snapshot_display`，不过管线） | (186,96,147) | **+50** |
| 投屏画面 | (206,94,143) | **+48** |
| 对照：股票 App 红字 | (233,79,77) | −2（真红） |

排除实验：纯红细字走 JPEG 4:2:0，B−G 最多 +10，**不可能产生 +48**。
→ **不要再去改色彩公式**（会破坏已验证正确的白底）。

## 2. 下一步（按优先级）

### 🥇 P0 —— 首帧优化（已定位根因，**尚未动手**）

实测启动时间线（`tmp/q_ds1_ref.log`）：

| 阶段 | 耗时 |
|---|---|
| 触控通道初始化 | ~1.0s |
| 采集初始化（tconn / 杀 daemon / so 校验 / **固定等 1.5s**） | ~3.3s |
| gRPC 握手 | ~1.8s |
| **等首帧** | **~10.2s** ⚠️ 最大浪费 |

**根因**：看门狗是「每 3s 轮询、空闲超 3s 才催 IDR」→ 启动后**最多纯等 6s 才发第一次催帧**。

**建议动作**（按收益排序）：
1. **gRPC 握手完成后立刻主动催一次 IDR**，不等看门狗 → 预期省 **4~6s**（复用现有 `h2.RequestAsync("/ScrcpyService/onRequestIDRFrame")`）
2. 并行化「触控通道」与「视频采集」初始化 → 省 1~2s
3. `start-daemon` 后固定 1.5s 改轮询就绪 → 省 ~1s

**⛔ 明确不要做**：为缩短首帧加 `power-shell wakeup` —— 代码旁有实测记录，加了之后出帧从 8 掉到 0。

## 4. 🔴 硬规则（必须遵守，违反会浪费大量时间）

### 操作纪律
1. **所有调试一律走无线**，统一入口 `scripts/hdcw.sh`，**禁止 USB**（插线会踢掉 TCP 通道）
2. **禁止并发调用 hdc**（两条并行 = 会话立刻死）
3. **编译/装机必须逐次授权** —— 改完不等于可以编译，要问「现在可以编译吗」
4. **回复第一行必须标注执行通道**（`MCP` 或 `命令行`）

### 本轮新踩的坑（血泪）
5. **`hdcw.sh` 的输出走 stderr** —— Python 里只读 stdout 会拿到空串，导致清理/判定**全部静默失效**（我因此白跑三轮）。必须 stdout+stderr 合并读取
6. **fport 会累积残留转发**（本轮积到 10 条）。取 `uitest_socket` 端口必须取**最后一条**（最新），否则滑动发到废弃端口 → 表现为「滑动无反应 / 流停滞」假故障。清理需循环两遍以上
7. **设置页/新闻页每次打开滚动位置不同** → 跨组内容不可比。对比前必须先验证内容相关度（corr>0.99 才可用）
8. **`--snapshot` 延时从「采集启动后」才开始计**，而采集本身要 8~11s → 等待要给足
9. **平板息屏会伪造「0 帧」** → 测试前必须 `power-shell wakeup`
10. **`aa start` 走 hdc 会踢掉 exe 的 fport** → 目标页面必须在**启动 exe 之前**打开
